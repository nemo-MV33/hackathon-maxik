## Что сохранять при обновлении

Тома `norfly_norfly-data` и `norfly_norfly-schedule` сохраняются при пересоздании контейнера. В первом находятся профили, общее и личное ДЗ, отметки переноса, история, снимки расписания и кэш. Во втором — выгрузка расписания мини-приложения и `meta.json`; его `fullUpdatedAt` сохраняет недельный интервал полной выгрузки между перезапусками. Не выполнять `docker compose down -v` и не удалять тома.

Перед выпуском сохранить текущий образ и копию томов в `/home/yc-user/norfly-releases/<дата-время>/`. Это разовая копия для отката выпуска; регулярные резервные копии остаются задачей этапа 4. Папка выпуска закрыта правами `700`, архивы — `600`.

## Порядок выпуска

1. Проверить `git status`, `npm test`, `npm run build:web`, YAML настоящим парсером и отсутствие строк `Co-authored-by` в новых коммитах.
2. Отправить ветку `main` в `origin`. Пуш сам по себе не запускает деплой: CI-деплоя в репозитории нет.
3. Сохранить прежний образ и данные на ВМ. Перенести исходники через `git archive`, не копируя локальные `.env`, `node_modules` и `data`.
4. Из `/home/yc-user/norfly` выполнить `sudo GITHUB_SHA=<полный хеш выпуска> docker compose build norfly`. Сборка идёт при работающем старом контейнере.
5. После успешной сборки выполнить `sudo GITHUB_SHA=<полный хеш выпуска> docker compose up -d --no-build norfly`. Должен остаться один экземпляр бота с рабочим токеном.
6. Проверить `/health`, `/version.json`, состояние Docker healthcheck, выдачу фронтенда и отсутствие ошибок запуска. В `version.json` должны быть первые 12 символов хеша собранного выпуска.
7. Проверять личные методы без настоящих initData только на отказ `401`. Не создавать тестовые ДЗ, переносы и сообщения в живой группе.
8. Записать результат, хеш выпуска, путь копии и оставшиеся задачи в `FINAL-UPDATE.md`. Если после выпуска меняется только документация, её можно синхронизировать без пересборки; `version.json` продолжает указывать хеш работающего образа.

Пример переноса уже проверенного коммита:

```bash
norfly_release=$(git rev-parse HEAD)
git archive --format=tar "$norfly_release" | ssh -i ~/.ssh/norfly_yc yc-user@158.160.253.148 'tar -xf - -C /home/yc-user/norfly'
```

При наличии новых записей сначала нужна их совместимая обратная миграция; полная копия не должна быть единственным способом сохранить эти записи.

## Перед будущим выпуском этапа 3

Этап 3 локальный: пуш и деплой требуют отдельного разрешения владельца. `compose.yaml` подключает новый постоянный том `norfly-attachments` в `/app/attachments` и задаёт `ATTACHMENT_DIR`. Проверить итоговый `docker compose config`: путь не должен вести в слой контейнера или каталог статической раздачи. После запуска проверить mount через `docker inspect`, создание файла в томе и сохранность после пересоздания контейнера.

При переключении остановить запись старого процесса и сохранить согласованную пару томов: `norfly-data` и `norfly-attachments` (также сохранить прежний `norfly-schedule`). В каталоге релиза должен появиться `attachments-at-switch.tar.gz`, права `600`; архив необходимо проверить чтением списка файлов. Первый выпуск: если том ещё не существует, записать этот факт, создать том до старта нового процесса и проверить mount. Для следующих выпусков отсутствие архива вложений блокирует переключение. Проверить, что `ATTACHMENT_DIR` из `.env` не переопределяет ожидаемый каталог.

JSON Community мигрирует с версии 3 на 4. Профили остаются версии 3. Старый образ не поддерживает вложения: перед откатом остановить новый, сохранить новые JSON и файлы отдельно, сверить изменения после выпуска. Не восстанавливать только JSON или только файлы. Регулярные резервные копии здесь не настраиваются: это этап 4.
