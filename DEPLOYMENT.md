Архив 1 ГиБ: `(22 − 1) × 2,376 = 49,896 ₽/мес`; архив 5 ГиБ: `(110 − 1) × 2,376 = 258,984 ₽/мес`. Реальное сжатие и совпадение ежедневных/еженедельных точек уменьшают сумму. Один временный новый объект при ротации может увеличить пиковый объём на размер архива. При 5 ГиБ используется около 80 частей по 64 МиБ; 30 ежедневных загрузок с проверкой укладываются примерно в 2600 операций записи и 30 GET в месяц. Новый сервер или платный KMS не требуются. Расчёт не включает увеличение диска/ВМ и изменение тарифа после даты проверки.

### Подключение после разрешения

1. Уточнить `DEMO_MAX_IDS`, `DEMO_CHAT_ID` и `BACKUP_ADMIN_ID`. Администратор и оба участника демо должны заранее нажать «Начать» в личном чате бота. Демо-чат закрытый; все участники входят в список разрешённых ID.
2. Создать согласованные выше ресурсы и политики. Записать S3-реквизиты в серверный `.env`, не заменяя остальные поля. Записать ключ отдельно, сохранить внешнюю копию. `BACKUP_KEY_FILE=/backup-secrets/key`, статус — `/backup/last-backup.json`, остальные параметры — `.env.example`.
3. Выпустить согласованный коммит обычным порядком выше. Скрипты `ops/` находятся на хосте из `git archive`; `scripts/` и серверные модули — в образе. Старый контейнер не умеет делать копии этапа 4.
4. Сначала один ручной запуск: `sudo sh ops/backup.sh`. Скрипт использует `flock`, определяет фактические три тома через inspect и проверяет работающий контейнер. Он останавливает приложение вместе с экспортёром, читает тома только для чтения и создаёт один зашифрованный архив. Сразу после шифрования приложение запускается; сеть и сверка идут при работающем приложении. Trap запускает приложение обратно и сообщает об ошибке.
5. Убедиться, что `/health` снова 200; статус `ok: true`, `snapshotAt` свежий. Лог — `sudo journalctl -u norfly-backup.service`; последняя попытка и последняя успешная точка — `sudo cat /var/lib/norfly-backup/last-backup.json`. Файлы содержат только служебные счётчики и имена объектов, без ключей и текста ДЗ.
6. Проверить реальное восстановление в отдельный каталог командой ниже, записать время и счётчики в FINAL-UPDATE.md. Не запускать восстановленный бот с рабочим токеном.
7. Только после успешной реальной проверки установить timer: скопировать `ops/norfly-backup.service` и `.timer` в `/etc/systemd/system/`, выполнить `sudo systemctl daemon-reload` и `sudo systemctl enable --now norfly-backup.timer`. Расписание — ежедневно 19:00 UTC, то есть 03:00 по Иркутску, случайная задержка до 5 минут, пропущенный запуск выполняется после старта ВМ.

Копия включает JSON, кэши, снимки, выгрузку расписания и байты/метаданные вложений. Корень ключа находится за пределами всех трёх томов. Архивы больше 64 МиБ загружаются частями; незавершённая загрузка отменяется при ошибке. До шифрования проверяется место под несжатый объём × 1,02 + 512 МиБ; архив удаляется после успешной отправки до обратного скачивания. На диске нужен примерно один дополнительный полный архив, а не несколько распакованных деревьев. Сверка при каждой копии потоковая: GCM, manifest, SHA-256, размеры и счётчики. Отдельная команда восстановления также сверяет уже записанные файлы.

У ВМ 20 ГБ: при полном томе вложений 5 ГиБ и бюджете ОС/данных 6 ГиБ ещё один архив 5 ГиБ и резерв 512 МиБ помещаются в 18,63 ГиБ только при небольших JSON/кэше и без лишних образов/копий релизов. Перед включением проверить `df -h` и фактический объём томов. Недостаток места прекращает копию и вызывает уведомление; удаление старых релизов или расширение диска требует решения владельца. Факт на 18.10.2026: `/` 19G, занято 3.6G, свободно 16G; контейнер один, healthy. Полная квота 5 ГиБ на проде не заполнялась для испытания.

### Проверка восстановления

На отдельной машине с Node.js 20, ключом и S3-реквизитами (или в служебном контейнере) выполнить:

```bash
BACKUP_KEY_FILE=/secure/norfly/key npm run backup:restore -- /absolute/new-empty-directory
```

На сервере без установленного npm восстановление выполняется через уже собранный образ:

```bash
sudo mkdir -m 700 /var/tmp/norfly-restore-check
sudo docker compose run --rm --no-deps \
  -v /etc/norfly-backup:/backup-secrets:ro \
  -v /var/tmp/norfly-restore-check:/restore \
  --entrypoint npm norfly run backup:restore -- /restore/latest
```

Команда выбирает последний архив по времени снимка, проверяет аутентичность до распаковки, запрещает симлинки и выход из каталога, восстанавливает в новый пустой каталог, затем сравнивает все SHA-256, размеры, состав файлов и счётчики JSON. Непустой каталог не заменяется. При повреждении последнего архива команда прекращается с ошибкой; автоматического скрытого перехода на более старую точку нет. Для выбора старой точки оператор должен явно скачать выбранный объект и вызвать `restoreArchive` либо временно использовать отдельный префикс. Не менять рабочие тома на этом этапе.

Для аварийного ввода восстановленной копии сначала подготовить ВМ в доступной зоне, доставить исходники **того же выпущенного коммита** и ключи из внешнего источника, остановить запись и сохранить текущие тома отдельно. Перенести `data`, `attachments`, `schedule` вместе; настроить `.env`/HTTPS, убедиться, что старый бот остановлен. Только затем запустить один контейнер, проверить версию, здоровье, авторизацию и контрольные счётчики. Перенос активных данных и переключение адреса требуют разрешения владельца.

**RPO/RTO:** при исправном ежедневном задании плановый RPO — до 24 ч 5 мин плюс длительность подготовки/отправки копии. При пропусках и ошибках верхняя граница не гарантируется; фактический возраст читается из `lastSuccess.snapshotAt`. Локальная проверка с подменой Object Storage восстанавливает 2 МиБ случайного вложения, общее/личное ДЗ, чат и снимок, со сверкой всех файлов. Реальный архив 3 341 659 байт, 20 094 файла: восстановление из облака на Node.js 20 ВМ — 37,434 с; отдельное восстановление вне ВМ с внешним ключом — 9,355 с вместе с LIST. Все SHA-256/счётчики совпали. Timer включён, last-backup.json ok=true; BACKUP_ADMIN_ID задан; тест оповещения принят MAX. Подробности в FINAL-UPDATE.md. Время развёртывания ВМ и HTTPS не входит во время распаковки; полный аварийный RTO пока не измерен. Нельзя выдавать локальные миллисекунды за обещание восстановления прода.

### Демо и финальный тег

На ВМ npm не установлен, используется npm внутри образа. Безопасный сброс: `sudo sh ops/demo-reset.sh`; скрипт останавливает бота/экспортёр, запускает `npm run demo:reset` в отдельном контейнере с `DEMO_RESET_OFFLINE=1`, затем возвращает приложение. Один `flock` исключает одновременную копию и сброс. Прямой сброс при работающем приложении запрещён: в памяти остаются старые JSON. Рабочие группы не меняются; неподтверждённые загрузки демо также очищаются. Контроль: исходное общее ДЗ «Решить задачи 1–3», переносов и личных версий нет, староста — первый ID, студент — второй, редакторы — остальные.

Только после выпуска и успешной проверки демо с настоящими MAX ID поставить локальный тег `git tag final-2026-10-29 <полный_хеш_выпуска>`. В FINAL-UPDATE.md и первый слайд записать именно хеш работающего образа, не более позднего коммита документации. Отправка тега требует разрешения на пуш. Тег пока не создан: требуется проверка переноса/фото/истории/уведомления двумя участниками в настоящем MAX с настроенными ID.
