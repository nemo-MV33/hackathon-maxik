# norfly — выпуск и передача следующему этапу

## Где работает приложение

- Прод: https://158-160-253-148.sslip.io, ВМ `norfly-app-d`.
- SSH: `yc-user@158.160.253.148`, существующий ключ `~/.ssh/norfly_yc`.
- Каталог на ВМ: `/home/yc-user/norfly`. Это выгрузка файлов, без `.git`.
- Запуск: `sudo docker compose` из каталога приложения; сервис `norfly`, контейнер `norfly-norfly-1`.
- Caddy принимает HTTPS. Порт приложения `3000` привязан к `127.0.0.1`; наружу его открывать не нужно.
- Серверный `.env` хранится только на ВМ. Его нельзя заменять примером или включать в Git.

## Что сохранять при обновлении

Тома `norfly_norfly-data` и `norfly_norfly-schedule` сохраняются при пересоздании контейнера. В первом находятся профили, общее и личное ДЗ, отметки переноса, история, снимки расписания и кэш. Во втором — выгрузка расписания мини-приложения. Не выполнять `docker compose down -v` и не удалять тома.

Перед выпуском сохранить текущий образ и копию томов в `/home/yc-user/norfly-releases/<дата-время>/`. Это разовая копия для отката выпуска; регулярные резервные копии остаются задачей этапа 4. Папка выпуска закрыта правами `700`, архивы — `600`.

## Порядок выпуска

1. Проверить `git status`, `npm test`, `npm run build:web`, YAML настоящим парсером и отсутствие строк `Co-authored-by` в новых коммитах.
2. Отправить ветку `main` в `origin`. Пуш сам по себе не запускает деплой: CI-деплоя в репозитории нет.
3. Сохранить прежний образ и данные на ВМ. Перенести исходники через `git archive`, не копируя локальные `.env`, `node_modules` и `data`.
4. Из `/home/yc-user/norfly` выполнить `sudo GITHUB_SHA=<полный хеш выпуска> docker compose build norfly`. Сборка идёт при работающем старом контейнере.
5. После успешной сборки выполнить `sudo GITHUB_SHA=<полный хеш выпуска> docker compose up -d --no-build norfly`. Должен остаться один экземпляр бота с рабочим токеном.
6. Проверить `/health`, `/version.json`, состояние Docker healthcheck, выдачу фронтенда и отсутствие ошибок запуска. В `version.json` должны быть первые 12 символов хеша собранного выпуска.
7. Проверять личные методы без настоящих initData только на отказ `401`. Не создавать тестовые ДЗ, переносы и сообщения в живой группе.
8. Записать результат, хеш выпуска, путь копии и оставшиеся задачи в `FINAL-UPDATE.md`. Если после выпуска меняется только документация, её можно синхронизировать без пересборки; `version.json` продолжает указывать хеш работающего образа.

Пример переноса уже проверенного коммита:

```bash
norfly_release=$(git rev-parse HEAD)
git archive --format=tar "$norfly_release" | ssh -i ~/.ssh/norfly_yc yc-user@158.160.253.148 'tar -xf - -C /home/yc-user/norfly'
```

## Откат

В папке выпуска записаны прежний хеш и тег сохранённого образа. Для отката вернуть этому образу тег `norfly-norfly:latest`, восстановить прежние исходники из `source.tar.gz`, затем выполнить `sudo docker compose up -d --no-build --force-recreate norfly`. Сначала сохранить состояние неудачного выпуска, чтобы не потерять новые записи пользователей.

Копию данных восстанавливать только при повреждении или несовместимости данных: обычный откат образа не требует удаления томов. Восстановление копии отменяет изменения после момента её создания. После отката повторить проверки здоровья и версии.

## Следующий этап

Этап 1 вводит совместимые поля `status`, `history`, `lessonChanges`, `scheduleOperations` и режим личного напоминания `lesson`. Старые записи читаются без отдельной миграции. Старый снимок расписания без типа занятия на первой проверке заменяется полным снимком версии 2 без рассылки и изменения ДЗ. Сравнивать изменения нужно с исходным расписанием (`raw: true`), оверлей применять только при чтении для студента.

Для этапа 2 сохранить единый путь `ScheduleService` и `LessonChangeService`: провайдер вуза должен возвращать те же нормализованные поля пары. Не обходить переносы и не возвращать мини-приложение к чтению только статических JSON. Сейчас идентификатор группы относится к ИРНИТУ; добавление идентификатора вуза и часового пояса — задача следующего этапа, она ещё не выполнена.

Демо `webapp/dev-data.ts` использует настоящие хранилища, маршруты и переносы. `?demoUser=1` — староста, `2` — студент, `3` — редактор. После изменения серверной логики перезапустить Vite перед проверкой. Сценарий и проверки описаны в `FINAL-UPDATE.md`.
